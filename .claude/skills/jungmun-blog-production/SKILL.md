# 중문매니저 블로그 제작

중문매니저의 검증된 제작·복구 경로를 재사용한다. 범용 검색 최적화 공식이 아니다. 사진 구조와 사용자의 수정을 보존하고 실제 저장 결과로 완료를 판정한다.

## Use When

- 중문매니저의 새 현장 글을 만들거나 기존 임시글의 사진·본문·썸네일을 수정할 때.
- 이 블로그의 제목·모바일 가독성·순차 썸네일 성공패턴을 재사용할 때.

## Inputs / Read First

- [프로젝트 STATUS.md](../../../docs/STATUS.md)의 목표·승인 범위와 가장 가까운 AGENTS.md/CLAUDE.md.
- 로컬 post.local.json (없으면 [예시](../../../post.example.json)): 현재 지역·제목·사진 경로·글자 수·브랜드·본문 정본.
- 아내분의 새 현장 인계는 [처음 시작 안내](../../../docs/아내_시작하기.md)를 사용한다. `현장작업/날짜_현장명/01_원본사진`에5~10장, `현장메모.txt`에 확인 사실을 둔다. 현장별 post.local.json을 사용한다.
- 이번 현장 사진, 확인된 지역/문 종류, 참고 PNG/GIF, 배너, 사용자의 최신 수동 수정. 과거 현장의 지역·사진 수·제품 정보를 새 글에 복사하지 않는다.
- 실제 편집/이미지 작업이면 [검증된 경로와 한계](references/success-patterns.md), 제목·노출 질문이면 [제목 근거](references/title-evidence.md)를 해당 부분만 읽는다.

## Steps

1. **변경 범위를 먼저 구분한다.** 제목 조사만이면 초안을 건드리지 않는다. 기존 글 수정이면 현재 제목·텍스트·사진 순서·대표선택·배너를 먼저 확인해 사용자의 수동 수정을 기준으로 삼는다. 읽을 수 없는 기존 상태는 확인한 것처럼 기록하지 않는다.
2. **사진에서 확인되는 내용으로 원고를 구성한다.** 새 현장은 `scripts/new_job.py`로 폴더를 만든다. 사진 수가 바뀌면 실제 파일명순 photo_001..N과 이미지 블록을 맞춘다. 사진·메모로 제목/원고/썸네일/태그/상담 링크를 확인한 후에만 `needs_authoring:false`로 바꾼다. 지역+중문+고객 고민/이익으로 짧은 제목을 쓴다. 숫자는 실제 본문의 항목 수와 일치할 때 선택한다. ‘숫자 제목’, ‘1800자’, 키워드 위치를 상위노출 보장 규칙으로 쓰지 않는다. 사진만으로 모델명·정확한 유리명·가격·단열수치·고객 후기를 지어내지 않는다.
3. **이 고객의 현재 서식을 적용한다.** 기본 본문1800자는 공백·소제목을 포함하고 줄바꿈·제목·이미지 속 글자·사진 자리표식·배너 아래 태그를 제외한다. 문장 중간은 의미 단위로 짧게 끊고 문장 끝은 빈 문단을 하나 넣어 두 번 내려쓴다. 세 군데 예외: 제목과 첫 PNG 사이에 빈 텍스트 컴포넌트를 추가하지 않는다. `안녕하세요.` 바로 다음 문단에 `**중문매니저**입니다.`를 배치한다(`gap_after:false`). 마지막 문장과 배너 사이 빈 문단은 최대 하나로 둔다. 나머지 문장 간격은 일괄 축소하지 않는다. 소제목은 에디터30+굵게, 본문16, 강조 단어만 굵게. 최신 사용자 지시가 기본값보다 우선한다.
4. **필요한 자산만 다시 만든다.** 설치된 Pillow 수치 보정으로 원본 구조·치수·원본 파일을 보존한다. 현재 브랜드 설정은 post.local.json을 사용한다. PNG/GIF에 같은 집 모양·명조 브랜드를 적용하고 GIF는 글자가 순차 등장한 뒤 완성 상태를 유지한다. 제목만 바꾸면 사진을 재업로드하지 않는다. Figma는 사용자가 원하거나 현 도구로 부족할 때 선택한다.
5. **현재 Umji의 정확한 초안을 편집한다.** 이 환경의 브라우저 작업은 문서화된 cua_repl로 한다. 다른 런타임이면 그 환경의 허용 도구를 먼저 확인하며 UI 우회나 내부 SmartEditor 모델 주입으로 대체하지 않는다. 기존 글은 사진 교체/본문 구간 교체를 사용하고, 새 글에만 전체 HTML의 자리표식 업로드 경로를 쓴다. 입력 이벤트 성공을 반영 완료로 간주하지 않는다.
6. **대표사진·배너·태그를 확인한다.** PNG만 대표로 선택한다. GIF는 본문에서 재생한다. 끝부분은 본문→내 템플릿 배너(실제 링크)→태그15개 순서다. 지역/동/아파트/확인된 문 종류·색/고객 관심/브랜드에서 내용과 직접 관련 있는 서로 다른 태그를 고른다. 검색량·상위노출을 측정한 것처럼 말하지 않는다. `태그_붙여넣기.html`을 배너 아래에 따로 붙인다(본문16/보통체/한 줄3개). 본문 해시태그와 네이버 발행 설정의 등록 태그는 별개다. 등록 태그는 발행 단계가 승인됐을 때 같은15개를 입력하고 확인한다. 사진 교체 후 대표선택이 해제될 수 있다. 기존 배너 보존 성공을 빈 글의 신규 템플릿 삽입 성공으로 확대하지 않는다.
7. **임시저장·새로고침·불러오기로 닫는다.** 원고 순서/글자 수/서식/사진 수/PNG대표/GIF/배너/태그/세 간격을 저장된 초안에서 다시 검사하고 확인 화면을 파일로 남긴다. 발행·통화는 이 스킬의 자동 후속이 아니다. 실제폰/공개목록/신규현장/전체10분은 각각 확인했을 때만 완료로 표시한다.

## Reuse / Outputs

실행 코드는 저장소 automation/을 참조하며 스킬 폴더에 복제하지 않는다. 최초 설치는 루트 README.md를 따른다. Windows는 [OS별 연결/검증](references/windows.md)을 읽고 platform을 명시한다. 아래 python은 .venv의 Python을 뜻한다.

```sh
python automation/build_assets.py --config post.local.json
python automation/build_assets.py --config post.local.json --check
python scripts/check.py
```

- `본문_1800자.txt`, `모바일_미리보기.html`, PNG/GIF·보정사진·manifest·검증 JSON.
- `태그.txt`, `태그_붙여넣기.html`은 배너 아래용 별도 산출물이다. 본문 HTML만 붙여 넣었다고 태그 배치 완료로 쓰지 않는다.
- 기존 사진 사이 텍스트만 수정: `구간별_본문.json` + `createNaverOps(ed, chromeApp, {platform}).replaceTextGroup(index, html)`.
- 사진만 수정: `replaceImage(index, absolutePath)` 후 PNG대표 재지정.
- 실제 편집기 검사: 최신 post.local.json을 읽어 `verifyEditor(ed, config)` 실행. stale config로 사용자가 수정한 제목을 덮어쓰지 않는다.
- 성공/실패·근거·다음 단계는 프로젝트 RESULTS.md/STATUS.md에 남긴다.

## Verify

- 로컬 검사와 실제 저장복원 검사는 별개다. 원본 지문·사진 구조, PNG/GIF 일치와 시각 디자인을 각각 확인한다.
- DOM의 각 비어 있지 않은 본문 문단이30/16 및 선택 단어 굵기와 일치하고, 실제 저장 글자 수가 목표와 같아야 한다.
- 구간 편집은 선택문 복사 대조와 사진 컴포넌트ID 전후 보존을 확인한다. 검사 코드가 던진 오류를 무시해 완료로 쓰지 않는다.
- 현재 실증: macOS/한국어/Umji 한 현장의 반복 수정. 코드/스킬 검증 통과와 새 현장 사용 실증을 구분한다.

## Failure / Fallback

- 로컬 파일 첨부가 확장 권한으로 막히면 OS 파일선택창 경로를 사용한다. 창·프로필이 달라졌으면 최신 상태로 원래 창을 찾는다. 계속 불일치하면 그 입력을 멈추고 나머지 로컬 결과는 보존한다.
- 화면 밖 GIF가 비어 보이면 인접 문단을 화면에 불러온 뒤 검사한다. 사진 유실로 단정해 재업로드하지 않는다.
- 소제목에서 본문 교체 시 굵기가 번지면 HTML의 `font-weight:normal`을 명시하고 필요한 strong만 남긴다.
- 브라우저/기존 코드 경로가 없으면 산출물·해당 단계의 한계를 보고한다. 설치·자동발행·보안 설정 변경으로 범위를 넓히지 않는다.
