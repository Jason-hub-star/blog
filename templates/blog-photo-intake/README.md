# 세 블로그 공통 사진 분리 가이드

배포판: 1.0 / 2026-11-01. 원본은 jason-agent-harness-template의 `templates/blog-photo-intake/`다. 각 브랜드 Git 브랜치에는 같은 배포판을 담는다.

## 작업자가 할 일은 세 가지

1. **브랜드부터 고른다.** 중문매니저·금강이지스·KB자동중문 프로젝트를 각각 다른 폴더로 연다. 같은 아파트여도 브랜드나 시공 현장이 다르면 섞지 않는다.
2. 이 폴더의 **`새현장`을 복사**해 프로젝트 루트의 `사진접수` 안에 넣는다. `2026-11-01_김포_현장A_자동중문`처럼 `수신일_지역_현장별칭_문종류`로 이름을 바꾼다. 같은 날 같은 이름이면 `_2`를 붙인다. 날짜는 수신일이며 실제 시공일은 메모에 따로 적는다. Windows에서도 쓸 수 있도록 `/ \\ : * ? " < > |`는 폴더명에 쓰지 않는다.
3. 아래 다섯 칸에 받은 파일을 **복사**하고 `현장메모.txt`를 적는다. 원본 이름을 바꾸거나 사진에 글자를 넣을 필요는 없다. `사진목록.csv`는 에이전트가 채운다.

이미 프로젝트에 `사진접수/사진수신_대기`가 있다면 그 빈 수신함부터 쓸 수 있다. 한 번 사용한 수신함에는 다른 현장 사진을 추가하지 않는다.

```text
사진접수/
  수신일_지역_현장별칭_문종류/
    01_시공전/       기존 문·철거 전·설치 전 공간
    02_시공후/       이번 시공이 끝난 문·열림·닫힘·마감
    03_확인필요/     전인지 후인지 모름·출처/현장이 불확실함
    04_영상/         열림→닫힘 원본 영상, 전후 시점은 메모
    05_참고자료/     로고·배너·제품 설명·다른 현장 참고·후기 캡처
    현장메모.txt
    사진목록.csv
    시작하기.txt
```

## 폴더를 고르는 기준

| 자료 | 넣을 곳 | 주의점 |
|---|---|---|
| 교체 전 기존 중문 | 01_시공전 | 문이 달려 있어도 이번 시공 전이면 전사진 |
| 설치자가 이번 시공 후라고 확인한 전체·상세 사진 | 02_시공후 | 확인자를 메모. 파일 날짜만으로 분류하지 않음 |
| 전후가 헷갈리거나 여러 현장이 섞인 사진 | 03_확인필요 | 억지로 시공 후로 정하지 않음 |
| 실제 개폐·열림 유지 등 동작 영상 | 04_영상 | 정지사진 효과 GIF와 실제 동작 영상은 구분 |
| 광고 시안·공식 로고·외부 사례·리뷰 화면 | 05_참고자료 | 이번 현장 시공사진으로 사용하지 않음. 리뷰는 상품·날짜·원문 링크도 기록 |

사진은 가능하면 원본 화질로 받고 원래 이름을 유지한다. 같은 이름의 파일이 서로 다른 폴더에 있으면 그대로 둘 수 있다. **같은 폴더에서 이름이 충돌하면 덮어쓰지 말고** `수신묶음_2` 같은 하위 폴더를 만들어 보존한다. 에이전트는 원본 상대경로 전체를 기록한다.

전후를 나눈 폴더도 사람의 최초 분류일 뿐이다. 에이전트가 문틀·유리·손잡이·레일 구조와 설치자 설명을 다시 대조한 뒤 확정한다. 고객 얼굴·동호수·차량번호 등 가릴 부분은 메모로 알린다.

## 촬영하면 좋은 장면

- 시공 후 **정면 닫힘 / 같은 각도 열림**: 대표 후보와 통행 공간 설명.
- **측면·신발장/현관문 간섭**, **바닥·하부 레일·문턱**: 선택 이유와 마감 설명.
- KB 자동중문은 **상부 센서·실내 버튼**, 고정 시점의 **열림→닫힘 영상**을 추가하면 좋다. 전원 방식은 설치자 확인과 구분한다.
- 전후 비교를 쓸 때는 같은 각도의 시공 전 사진을 함께 받는다. 전사진이 없으면 실제 후사진 중심으로 쓴다.

장수를 맞추기 위해 비슷한 사진을 채우지는 않는다. 중문매니저 제작기는 선별5~10장을 받으며, 금강이지스는 글별 필요 사진과 리뷰 캡처를 따로 정한다. KB 첫 글의 장수·분량은 실제 자료를 보고 정한다.

## 에이전트가 이어받을 때

1. 프로젝트 `AGENTS.md`와 목표 상태 문서를 읽고 브랜드·대상 계정·접수 현장·사용자의 최신 수정을 확인한다.
2. 받은 사진을 직접 보고 `사진목록.csv`에 **원본 상대경로 → 단계/근거 → 역할 → 게시순서 → 대표 → 작업사본명 → 원본 SHA256**을 기록한다. 작업자는 SHA나 JSON을 작성할 필요가 없다. 모르는 단계는 `unconfirmed`, 사용여부는 `pending`으로 둔다.
3. 확정된 사진만 새 제작 현장으로 **복사**한다. 수신 원본은 건드리지 않는다. 중복 파일명은 작업 사본에만 `001_before_front.jpg`, `002_after_closed.jpg`처럼 세 자리 게시순번을 붙이고 대응표에 남긴다. 확장자만 바꾸는 변환은 하지 않는다. HEIC 등은 원본을 보존하고 지원 형식의 사본을 별도로 만든다.
4. 아래 브랜드별 기존 제작 구조를 사용한다. 접수 하위 폴더를 기존 제작기에 그대로 넘기지 않는다. 이 양식 자체가 사진을 자동 분류하거나 제작기를 실행하지는 않는다.
   영상은 두 기존 사진 제작기의 자동 입력 대상이 아니다. `01_원본사진`에 동영상 파일을 넣지 말고 접수 원본으로 보존한 뒤, 실제 글에서 필요한 영상 첨부·스틸 추출을 별도로 정한다.
5. **대표 PNG/GIF의 바탕 사진은 확인된 after 한 장으로 명시**한다. 게시순서 첫 장과 대표사진을 별도로 선택한다. before·unconfirmed를 대표로 사용하지 않는다.
6. 원본 지문과 사본 대응·사진/영상·본문 배치·브랜드별 설정을 검사한다. 네이버에서는 임시저장→새로고침→재불러오기까지 통과해야 실제 저장 완료다.

| 브랜드 | Git 브랜치 | 확정 사진의 기존 제작 위치 | 에이전트가 할 일 |
|---|---|---|---|
| 중문매니저 | main | 현장작업/고유현장/01_원본사진 | new_job.py로 생성 후 선별 사본5~10장, 실제 파일명순 photo_001..N·thumbnail_photo·본문 블록을 일치시킴 |
| 금강이지스 | geumgang-aegis | 현장작업/고유현장/01_원본사진, 01_리뷰캡처 | setup의 새_현장 가상 예시를 고유 폴더로 복사하고 새 원본목록·photo_stages·cover·리뷰 출처를 작성. --job 명시 |
| KB자동중문 | kb-autodoor | 현장작업/고유현장/01_원본사진 | 접수·배치부터 확인. 아직 KB 렌더러·업로드·저장복원은 첫 현장 검증 전 |

기존 현장을 예시 폴더처럼 복사해 새 글을 만들지 않는다. 특히 금강이지스 사용자가 삭제한 사진·전후 콜라주와 개별 리뷰는 해당 기존 글의 상태이며 새 현장으로 옮기지 않는다.

## 통일할 범위

**통일한다:** 브랜드→현장→받은 자료 구분, 다섯 수신 폴더, 원본 이름 보존, 사실 메모와 사진목록, 확인된 후사진 대표, 원본/작업 사본 대응, 저장복원 완료 판정.

**브랜드별로 유지한다:** 기존 제작 폴더·설정 형식, 글 분량·정렬·글자 크기, 로고·색·PNG/GIF 디자인, 배너·링크·템플릿·리뷰 연결. 중문매니저의 본문16·1800자와 금강이지스의 본문15·1500~1800자를 서로 적용하지 않는다. KB 규칙도 따로 확정한다.

이렇게 하면 작업자는 같은 방법으로 자료를 전달하고 검증된 제작 도구는 유지할 수 있다. 제작기 전체 통합은 현재 필요한 사진 접수 개선보다 변경 범위가 커서 보류한다. 첫 신규 현장에서 접수→선별 시간을 재고 필요할 때 자동 연결만 추가한다.

## Git과 다른 컴퓨터

Git에는 빈 양식과 일반 안내만 공유한다. 실제 `사진접수/`·`현장작업/` 자료와 메모/사진목록은 비공개로 별도 전달한다. 중문매니저는 해당 현장 폴더와 필요하면 접수 폴더를 같은 상대경로로 복사한다. 금강이지스의 `scripts/package_transfer.py`는 제작자료를 묶고, 공통 `사진접수/` 원본도 함께 보관하려면 해당 접수 폴더를 별도로 전달한다.

새 컴퓨터에서 각 브랜치를 **별도 폴더로 clone**한다. 한 폴더에서 브랜드 브랜치를 번갈아 바꾸지 않는다. 현재 자료는 이동하지 않고 기존 경로에서 계속 사용할 수 있다.
