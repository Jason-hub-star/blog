판정: 로컬/실제 Mac 초안 범위 **ready-to-share**. Windows 실제 네이버 UI와 전체10분은 미검증이다. 목표·승인 범위는 [STATUS](../../STATUS.md)에 유지한다.

## 실제 실행

- `.venv/bin/python scripts/check.py` →0. 합성7장 자산/1800자/태그/폰트/원본, 새 현장5/10장 복사·상대경로·무덮어쓰기·작성상태, OS별 복사/파일창 모의 검사 통과.
- `python3 -S scripts/check.py` →2. Pillow 없는 환경을 판정 불가로 처리했으며 통과로 오인하지 않았다.
- skill-creator의 quick_validate.py로 정본 스킬 검증 →0.
- 실제 설정으로 새 현장 폴더 생성→해당 설정으로 build_assets.py 실행→14가지 로컬 자산 검사 PASS.7개 원본 복사와 기존 대비9개 미디어 바이트 동일 확인.
- 실제 Umji 편집기에서 태그 추가 전후 사진10개 ID 및 기존 본문/빈 문단 전부 동일 확인. 임시저장→새로고침→목록의 해당 제목 불러오기→verifyEditor16조건 PASS.

실제 편집기16조건: 제목, 원고 순서, 본문1800자, 소제목30굵게, 선택 단어만 굵게, 본문16, 문장 간격(인사 예외), 사진10개, PNG단독대표, GIF, 하단 배너 링크 아이콘, 자리표식 없음, 배너 아래 태그15개/본문16보통체, 인사 붙임, 배너 앞 빈 문단 최대1개, 첫PNG 앞 빈 텍스트 없음.

확인 화면/DOM JSON/실제 원고는 로컬 `현장작업/2026-11-01_성남_여수동_산들마을아파트/03_작업결과`에 보존했다. 공개 저장소에는 올리지 않는다. 제목/썸네일 간격40px은 현재 화면의 관찰값이며 다른 OS에 고정하지 않는다.

## 감사에서 확인·수정한 문제

`evidence-audit`의 표준 검토로 상태 보존·인계 흐름·공개 Git 범위를 확인했다.

- 새 현장에 사진이 있어도 예시 원고가 바로 생성될 수 있던 경로: 모든 새 현장에 needs_authoring을 설정하고 생성기에서 작성 확인 전 거절하도록 수정. 거절 검사 통과.
- 다른 위치의 설정을 복사하면 상대 배너 경로가 깨지는 경로: 원본 설정 기준으로 해석하고 현장 참고 폴더에 복사, 새 상대경로 저장. 전용 검사 통과.
- 파일 정렬 차이로 사진 번호가 달라질 수 있던 경로: 폴더 생성기와 제작기에 같은 파일명 정렬 사용.
- 독립 읽기 리뷰의 P1(CLOSED): Windows 다른 드라이브 폰트의 relpath 오류가 사진 복사 뒤 발생하던 문제. 폰트 존재/상대경로 계산을 폴더 생성 전에 끝내고, 다른 드라이브 폰트는 명확히 거절한다. 오류 주입 검사로 폴더 미생성을 확인했다. 다른 드라이브의 사진 입력은 복사할 수 있다.
- 본문 태그를1800자에 합치면 기존 글자 수가 달라지는 경로: 마지막 배너 앞 본문과 뒤 태그를 분리해 실제 편집기로 확인.

남은 범위: 발행 설정의 등록 태그, 공개 목록 PNG 노출, 실제 휴대폰, Windows 네이버 실기, 빈 글에서 신규 내 템플릿 삽입, 전체10분. 이번 작업에서 발행/통화는 하지 않았다. 지역/사진 장수/제품 정보는 다음 현장에 자동 이월하지 않는다.

## 결정·회고

- 폴더: 한 현장에 하나, 원본/참고/결과 분리. 기존 폴더 덮어쓰기 대신 다른 현장명을 사용한다. 단일 data/photos에 여러 현장을 섞는 방식은 기본 인계에서 제외했다.
- 반복 수작업 → 새 현장 폴더·메모·상대경로를 new_job.py로 생성한다.
- 되돌린 가정 → 사진 복사 완료는 현장 원고 확인 완료가 아니다; needs_authoring으로 구분한다.
- 다음 재탐색 방지 → 아내분 시작 안내와 PROJECT-STATUS의 첫 명령을 남겼다.

기존 Git 공유 요청 범위로 공개 코드·스킬·문서만 지정 저장소에 반영한다. /마감 자체를 자동 push 권한으로 해석하지 않는다.
